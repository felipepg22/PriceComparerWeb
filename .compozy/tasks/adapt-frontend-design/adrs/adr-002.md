# ADR-002: Split Dashboard Into Presentational Components

## Status

Accepted

## Date

2026-05-17

## Context

The current Angular frontend is a single standalone `App` component that owns the reactive search form, local signal state, API call, result rendering, and component-scoped styling. The redesign in `client/DESIGN.md` requires a richer dashboard layout with a search workspace, metrics summary, offer cards, empty state, loading state, and error state.

The implementation must preserve the existing backend contract and avoid backend changes. It must also hide detailed failed-source diagnostics from the main user experience while keeping attempted-source breadth visible through summary metrics.

## Decision

Split the redesigned dashboard into small standalone presentational Angular components for the search surface, metrics summary, offer list or offer cards, and state messaging. Keep API state, reactive form ownership, request submission, and derived display helpers in the root `App` component. Pass prepared inputs into child components and emit search events upward from the search component.

The frontend will preserve API offer order. It will show confidence as a percentage plus a derived High, Medium, or Low label, but it will not reorder or rank offers. Partial failures will not render as a dedicated notice or detailed list in the main dashboard.

## Alternatives Considered

### Alternative 1: Keep a single root component

- **Description**: Implement the redesign entirely inside `App`.
- **Pros**: Smallest file count and minimal wiring.
- **Cons**: The richer dashboard markup would make the root component harder to scan and test.
- **Why rejected**: The redesign has multiple visual regions with clear boundaries, and presentational components keep those boundaries explicit without changing the backend contract.

### Alternative 2: Add a frontend service or facade first

- **Description**: Introduce a service for API access and view-model mapping before changing layout.
- **Pros**: Cleaner separation for future growth.
- **Cons**: Adds indirection that the current single-page workflow does not need.
- **Why rejected**: The MVP can preserve the existing local state and API call path while still improving component structure.

### Alternative 3: Client-side offer sorting or ranking

- **Description**: Sort offers by lowest price or highlight the strongest confidence result.
- **Pros**: Could make the list feel more decisive.
- **Cons**: Risks implying a ranking algorithm that the backend does not provide and may hide meaningful API ordering.
- **Why rejected**: The dashboard should use visual hierarchy and confidence labels without changing result semantics.

## Consequences

### Positive

- The redesigned markup is easier to maintain and test by UI region.
- The backend contract remains unchanged.
- Display logic remains centralized in `App`, keeping child components simple.
- The UI avoids overstating ranking or completeness.

### Negative

- The frontend gains several files for a currently small app.
- Root-to-child input wiring adds light ceremony.
- Detailed failed-source diagnostics are no longer available in the main UI.

### Risks

- Component splitting could drift into premature abstraction. Mitigate by keeping components presentational and avoiding new services unless implementation proves they are necessary.
- Hiding partial failures could reduce transparency. Mitigate by preserving attempted-source counts and clear API error states.

## Implementation Notes

Use Angular 21 standalone components and existing signal/reactive-form patterns. Add focused tests for the root workflow and key presentational states. Keep currency options and `POST http://localhost:5235/api/products/search` unchanged.
